smolagents 负责“请求模型—解析工具—回传结果”的循环；我们的代码负责执行许可。完成声明也必须走同一个入口。

# 这个方法属于继承 ToolCallingAgent 的 GuardedAgent；这里只接管工具入口，不重写框架循环。
def execute_tool_call(self, tool_name, arguments):
    # self.h 是宿主 Harness，gate 是统一门禁对象；点号表示取对象属性。
    # 框架解析完工具名和参数后，实际执行必须先经过 dispatch。
    result = self.h.gate.dispatch(self.call_id, tool_name, arguments)
    # dict.get("ok") 取字段；字段不存在时返回 None。not 会把空值/False 判为真。
    # 特别处理 final_answer：返回一个“拒绝字典”仍可能被框架视为结束，必须抛框架异常。
    if tool_name == 'final_answer' and not result.get('ok'):
        # raise 会沿调用栈退出，交给框架捕获；框架得到失败原因后可继续下一轮。
        # 不要把它当成 C 的单纯错误码返回：调用者必须有对应的异常处理路径。
        raise AgentToolExecutionError(json.dumps(result), self.logger)
    return result

def path(self, name: str, write=False) -> Path:
    """同时检查文本路径和真实落点；拒绝所有软链接，避免链接到敏感文件。"""
    # Path 是路径对象，封装了路径拼接与解析；不是直接拼字符串。
    rel = Path(name)
    # 只接受工作区内相对路径；rel.parts 把目录逐段拆开，检查 .. 逃逸。
    if rel.is_absolute() or '..' in rel.parts or not rel.parts:
        raise BoundaryError('PATH_ESCAPE')
    # 逐个路径段检查敏感名，.env 及其变体也禁止通过工具访问。
    if any(p in SENSITIVE or p.startswith('.env') for p in rel.parts):
        raise BoundaryError('SENSITIVE_PATH')
    # Path 的 / 运算符用于拼接路径，这里的 / 不是数值除法。
    candidate = self.root / rel
    # *candidate.parents 会把各级父路径展开到列表，类似把数组元素逐个追加进去。
    # 检查每一级软链接；否则“工作区内文件名”可能指向工作区外。
    for part in [candidate, *candidate.parents]:
        if part == self.root:
            break
        if part.is_symlink():
            raise BoundaryError('SYMLINK_DENIED')
    # resolve 解析真实落点，再确认它仍在 root 下；cwd 不是文件访问权限边界。
    if not candidate.resolve().is_relative_to(self.root):
        raise BoundaryError('PATH_ESCAPE')
    # 写入只放行 Python 源文件与 artifacts 下的 Markdown；测试禁写由外层 Gate 再限制。
    if write and (rel.suffix != '.py' and not (rel.parts[0] == 'artifacts' and rel.suffix == '.md')):
        raise BoundaryError('WRITE_SCOPE')
    return candidate

设计 04

业务状态独立于模型对话

对话说明模型说过什么；业务状态记录运行到哪一步。RUNNING、WAITING_APPROVAL、UNKNOWN_RESULT 等状态通过统一入口迁移。

guarded_harness/state_store.py:56
# to 是目标状态，event 是触发事件。reason=None 表示省略时没有附加原因。
def transition(self, event, to, reason=None):
    """统一入口：检查合法迁移，序号跨进程延续，审计另保留外部事件。"""
    # 这里没有复制字典：state 和 self.data 指向同一个可变对象。
    # 可类比 C 的两个指针指向同一个 struct；通过 state 修改会直接改变业务状态。
    state = self.data
    old = state['status']
    # ALLOWED 是“旧状态 → 允许目标状态集合”的表，集中约束状态迁移。
    # .get(old, set()) 表示键不存在时使用空集合；终态不能随意跳回 RUNNING。
    if to not in ALLOWED.get(old, set()):
        raise ValueError(f'非法状态迁移：{old} -> {to} ({event})')
    # append 往历史列表尾部加一条记录；dict(...) 创建一条映射记录。
    # 恢复时历史列表也会恢复，len + 1 因而接着原序号往下记。
    state['transitions'].append(dict(seq=len(state['transitions']) + 1, event=event,
                                     from_state=old, to_state=to, reason=reason))
    # update 原地修改指定字段，不会替换其他业务字段。
    state.update(status=to, stop_reason=reason)
    # [-1] 取最后一个元素；在 C 中通常要写 array[length - 1]。
    return state['transitions'][-1]

把计划变成有依赖、可验收的步骤

修复计划是 inspect → change → verify → finalize。每步存目标、依赖、状态、尝试次数与结果记录 ID；改完源码后，旧验证步骤退回待验证。

def begin(self, id):
    # depends_on 存前置步骤 ID；dependencies 返回尚未完成的依赖。
    missing = self.dependencies(id)
    # 非空列表在 if 中为真，类似 C 中判断 missing_count != 0。
    if missing:
        raise ValueError('步骤依赖未完成：' + ', '.join(missing))
    # get 返回计划里原有步骤字典的引用；下面修改的是实际计划，而非临时副本。
    step = self.get(id)
    # 记录尝试次数，与工具是否成功是两回事；恢复后也保留。
    step['attempts'] += 1
    # 重读文件不抹掉已经建立的理解事实；重跑验证必须撤回此前“完成”。
    # 已经建立的源码阅读事实不因再次阅读而清零；验证步骤每次重跑则重新进入执行中。
    if id != 'inspect' or step['status'] != 'completed':

# 开始步骤和完成步骤分开：只有执行结束后，才能按真实结果更新状态。
def observe(self, id, evidence=None, success=True, error=None):
    step = self.get(id)
    # evidence 是程序产生的结果记录，id 关联到具体工具调用；模型不能自行宣称有记录。
    if evidence and evidence['id'] not in step['evidence_ids']:
        step['evidence_ids'].append(evidence['id'])
    # A if condition else B 是 Python 条件表达式，对应 C 的 condition ? A : B。
    # 完成必须由 success 决定；异常和失败也要留下状态与错误信息。
    step.update(status='completed' if success else 'failed', last_error=error)

设计 07

由完成契约验收，最后一次测试说了算

模型调用 final_answer 只是在申请结束。程序分别检查修复或理解任务的全部缺项，把具体原因反馈给模型继续补齐。

guarded_harness/completion.py:25
def latest_test(evidence, scope='all'):
    # 先找最新“尝试”，再判断成功；失败/超时/取消/未知不能被旧通过遮住。
    # 这是生成器表达式，不是立即建立新列表；每次只取一个符合条件的元素。
    # reversed 从尾部往前遍历；next(..., None) 取第一个匹配项，没有就返回 None。
    # 可类比 C 的逆序 for：找到同一 scope 的最近记录后 break。
    # 必须先找最新尝试，再判断成功；不能先筛“通过项”，否则会漏掉更晚的失败。
    return next((e for e in reversed(evidence) if e['kind'] == 'test' and e.get('scope', 'all') == scope), None)

def test_issue(evidence, revision):
    latest = latest_test(evidence)
    # 没有记录先返回缺项；不能把“未跑测试”当作默认成功。
    if not latest:
        return issue('MISSING_CURRENT_TEST', '尚未执行当前版本测试，请调用 run_test。')
    # 内容哈希要和当前版本相同；测试后又改代码，旧通过立即失效。
    if latest.get('revision') != revision:
        return issue('STALE_TEST', '最新测试不属于当前源码版本，请重新运行 run_test。')
    # reason 包括超时、取消和结果未知；退出码非零也不能交付。
    if latest.get('reason') or latest.get('returncode') != 0:

设计 09

状态用于恢复，审计用于解释原因

Checkpoint 保存当前可恢复现场；Audit 追加记录曾发生的批准、拒绝和执行结果。二者各做一件事。哈希链能发现已有行被改写，但没有外部锚点时不能阻止整条链被重写。

# **details 接收其余命名参数，组成一个 dict；它不是 C 可变参数的无类型内存读取。
def record(self, rule, decision, tool_call_id=None, actor='program', **details):
    # run_id 关联整个任务；tool_call_id 关联某次动作；actor 标明谁作出决定。
    item = dict(time=datetime.now(timezone.utc).isoformat(), run_id=self.run_id,
                rule=rule, decision=decision, actor=actor, tool_call_id=tool_call_id,
                # 把上一条哈希写进本条，形成前后关联。字典里的 **details 表示合并额外键值。
                previous=self.previous, **details)
    # digest 对结构化内容算 SHA-256。先算当前条目，再把 hash 加进去，避免自引用。
    item['hash'] = digest(item)
    # 'a' 是追加模式，类似 C 的 fopen(path, "a")；不会覆盖之前的行。
    with self.path.open('a') as f:
        # 每行一个 JSON 对象，行与行独立，便于按调用 ID 查询。
        f.write(json.dumps(item, ensure_ascii=False) + '\n')
        f.flush()
        os.fsync(f.fileno())
    # 保存当前哈希，下一次 record 将把它作为 previous 使用。
    self.previous = item['hash']
    return item

学完应该掌握的 9 个判断

参考答案按课程 3-1 的循环分工、3-3 的状态与恢复、3-5 的完成契约和 3-7 的预算治理整理，并注明本作业的实际边界。

  1. 能指出模型决策和程序执行的边界，解释为什么不用重写 Agent 循环。

    模型负责提出下一步动作，程序负责校验、审批、执行、记录和验收。smolagents 已有多轮循环，我们只在工具入口和完成检查处增加约束。本作业继承 ToolCallingAgent，模型返回结构化工具调用；生成并执行 Python 代码的是另一种 CodeAgent。

  2. 能解释参数、重复调用和写入审批为什么必须在执行前检查。

    文件一旦写入，事后拒绝并不能撤销副作用，因此门禁必须先于 handler。参数检查保证调用符合契约；同一调用 ID 不重复消费，相同动作连续第三次被拦截；写入审批绑定参数签名和当前源码版本，防止改参数或换代码后复用旧批准。

  3. 能区分路径/命令限制与操作系统隔离，知道当前 Sandbox 的能力边界。

    当前 Sandbox 校验工具路径、限制固定测试命令、清理子进程环境，并管理超时、输出和进程组。这些只约束受控执行入口：pytest 内的 Python 代码仍有当前用户权限，能绕过工具直接访问宿主文件或联网。运行不可信仓库需要另加容器/虚拟机以及文件、网络和资源隔离。

  4. 能沿状态迁移历史说明一次任务为什么暂停或停止。

    按序号查看 from_state → event → to_state，再看 reason 与 stop_reason。WAITING_APPROVAL 表示等待决定，不是失败；UNKNOWN_RESULT 表示执行结果待核对；NEEDS_REVIEW 表示现场变化使旧依据失效；预算耗尽则明确 STOPPED。只有完成契约通过，才是 COMPLETED，而不是“循环结束就算成功”。

  5. 能区分“工具返回成功”“步骤完成”“任务完成”。

    工具成功只说明一次调用得到预期返回；步骤完成还要求前置依赖和该步骤的真实结果满足标准；任务完成要求所有必要步骤及整体完成契约通过。例如“文件写成功”不等于“修复完成”：还要核对当前源码差异、未被篡改的测试，以及最后一次有效测试通过。理解任务则需要当前源码阅读和约定报告。

  6. 能解释写入结果未知为什么不能自动重试，且能使用 inspect 判断现场。

    执行顺序是存 EXECUTING → 执行副作用 → 存 DONE；两次存档之间崩溃，文件可能已改，直接重试会重复副作用。inspect 只读检查存档结构/校验和、工作区变化和未闭合调用：READY 可恢复，WAITING_APPROVAL 先审批；UNKNOWN_RESULT 或 WORKSPACE_CHANGED 先人工核对，本实现核对后另建 run，不自动重放未知写入。

  7. 能判断一条测试记录是否是当前版本的最后一次有效通过。

    先取同一测试范围的最后一次尝试，再检查它是否通过，不能先筛选成功记录。有效条件是退出码为 0、没有超时/取消/未知原因、测试前后输入稳定，且记录指纹与当前源码、测试及相关配置一致。后来的失败会挡住旧通过；源码再变更后必须重测。

  8. 能说明累计预算如何跨进程保留，以及上下文压缩保留了什么。

    轮数、调用数、累计 token 和有效运行耗时写入 Checkpoint，恢复时延续计数，等待人工的暂停时间不累计。上下文保留系统/任务指令和近期完整工具交互，旧步骤用确定性摘要替代，完整事实仍留在本地；指令装不下就停止。token 在请求边界检查，已发出的单次请求可能超额，因此不是账单硬上限。

  9. 能沿调用 ID 找到批准、拒绝和执行的关联，而不是只相信模型自述。

    用 run_id 找整次运行，再用 tool_call_id 串起 WAIT/DENY、批准者 actor 的 ALLOW，以及执行 START/DONE 和结果。同一次动作有批准记录，不代表已经落盘；还要核对实际文件、内容哈希和当前测试。模型说“已修好”只是声明，不能替代程序产生的执行记录和完成验收。
