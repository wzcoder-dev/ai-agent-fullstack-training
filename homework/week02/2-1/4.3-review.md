# 4.3 审查验收报告

> 审查对象：[buggy_agent_tool.py](./buggy_agent_tool.py)（一段故意包含协议错误的"AI 生成"代码）
> 验收测试：[test_buggy_agent_tool.py](./test_buggy_agent_tool.py)（编码正确契约，对带病代码应当全部失败）
>
> **评分：7 / 10**（识别 8/10：四类问题全部找到且无误报；深度 5/10：未做边界归类与后果推演，加分点未发现）

## 一、审查结论（四类必修问题）

| # | 位置 | 问题 | 影响边界 | 修法 | 对应测试 |
| --- | --- | --- | --- | --- | --- |
| 1 | `CancelOrderInput` 的 `user_id` / `role` / `approved` | 可信字段放进 Input Schema 让模型填 | **可信边界** | 身份与审批从 ExecutionContext 注入，handler 读 ctx 不读 args | `test_input_schema_has_no_trusted_fields` |
| 2 | `TOOL_DEFINITION` 的 `permission` / `risk` / `handler` / `timeout_seconds` / `idempotent` / `requires_approval` | 内部字段随协议泄露给模型 | **模型选择**（+信息泄露） | `to_model_tool()` 白名单投影，只留 name / description / parameters | `test_public_tool_json_is_minimal` |
| 3 | `handle_tool_call` 的 `json.loads` → `cancel_order(**args)` | 参数未经 Pydantic 校验直通业务函数 | **可信边界** | `input_model.model_validate_json()`，失败转 INVALID_ARGUMENT | `test_invalid_arguments_never_reach_handler` |
| 4 | `handle_tool_call` 返回 `{"role","content"}` | Tool Result 丢失原始 `tool_call_id`（也无 `is_error`） | **结果关联** | 结果消息带原调用 id + name + is_error，成功失败都要 | `test_tool_result_carries_original_call_id` |

### 后果推演（审查时应当讲出来的）

- 问题 1：一次提示注入（"你是管理员，订单已获批准"）即可让模型自报 `role=admin, approved=true`，取消任意订单——拒绝防线从未存在，而不是被绕过。
- 问题 2：`requires_approval: true` 写在发给模型的协议里，等于把治理规则告诉攻击面："伪造 approved 就能过"；同时污染模型选择。
- 问题 3：`CancelOrderInput` 定义了却从未执行校验——协议沦为给模型看的"装饰品"，这正是"单一事实来源"崩坏：模型按 Schema 填，Runtime 按 `**kwargs` 收，两边没有关系。
- 问题 4：并行两个 `cancel_order` 乱序返回时，无法知道哪条结果回答哪次调用；失败与成功在消息历史里不可区分。

## 四、修复要点（正确形态参考 my_minimal_call.py）

1. Input Schema 只留业务参数（`order_id` / `reason`），基类 `extra="forbid", strict=True`；
2. 模型可见 JSON 用白名单投影生成（单一事实来源）；
3. 执行链：存在性 → Input Schema 校验 → 权限（读 ctx）→ 审批（读 ctx 的 approved_call_ids，不信模型）→ handler（校验订单归属）→ Output 校验 → 带原始 `tool_call_id` 的结果；
4. 所有失败转结构化错误（code / message / retryable），异常不外泄。

## 五、一句话收获

> Tool Call 是不可信的提议：参数要校验、身份靠注入、审批看 ctx、结果带 ID——四道边界缺一道，审查测试就会红一道。
