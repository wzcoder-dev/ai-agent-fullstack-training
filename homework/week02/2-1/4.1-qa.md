## Q1. Function Calling 与普通函数调用有什么区别？（7 / 10）

**我的回答：**

> function calling 被调用后不能直接执行，是要经过校验、认证后才能去执行，而函数被调用是直接执行的。

**评分与点评：**

- ✅ 答对核心边界：Function Calling 是"提议"，必须经校验/授权后才执行；普通函数调用即调用即执行。
- ❌ 缺两点：① 发起方是不可信的模型，参数是一段 JSON 文本，与同信任域内的类型化调用有本质区别；② 结果不是"拿到返回值就结束"，而要变成带原始 `tool_call_id` 的 Tool Result 写回消息历史，驱动模型下一轮决策——这才是完整闭环。
- 扣分点：只答了"执行前"半段，没答"结果回写"半段。

**更优答案（两分钟版）：**

> 普通函数调用发生在同一信任域内：参数由类型系统保证，调用即执行。Function Calling 里，调用发起方是不可信的模型，它输出的只是一段结构化 JSON——工具名加参数，表示"我想调用什么"，是候选动作而不是执行许可；中间必须插入 Runtime 做参数校验、权限判断和风险控制，通过后才执行真实业务函数；执行结果无论成败，都要包装成带原始 tool_call_id 的 Tool Result 写回消息历史，作为 observation 交给模型继续决策。所以区别有三层：调用方不可信、提议与执行分离、结果要回写形成闭环。

## Q2. 模型侧 Tool 为什么没有 `execute()`？（6 / 10）

**我的回答：**

> 模型不应该直接执行工具，它是要选择工具，作为候补执行。

**评分与点评：**

- ✅ 方向对：模型职责是选择/提议，不是执行。
- ❌ 没答出"为什么"：模型侧只拿到公开协议（name / description / parameters），物理上就触达不了业务函数；如果模型侧带 `execute()`，等于让不可信输出直接驱动任意代码执行，绕过 Runtime 的校验、鉴权、风险控制与审计——即"治理旁路"。
- ❌ "作为候补执行"表述含糊，容易让人以为模型在某个环节还是会执行。

**更优答案（两分钟版）：**

> 因为发给模型的只是工具的公开协议：名称、描述和参数 Schema，handler 从头到尾不会暴露给模型。这样设计有两个理由：第一，模型输出是不可信数据，如果它自带 execute()，一段被注入或幻觉的输出就能直接变成任意代码执行，Runtime 里的校验、鉴权、风险分级和审计全部被绕过；第二，职责上模型只负责在协议内提出候选动作，执行是 Runtime 的事。参考 pi 的设计：Tool 元数据和执行函数是分离的，prepareToolCall 先校验参数、再过 hooks，执行始终在 Runtime 一侧，且全程沿用同一个调用 ID。

## Q3. Input、Output 和 Error Schema 分别约束什么？（5 / 10）

**我的回答：**

> input 是 name description arg 三个参数，告诉模型在什么时候调用工具和如何传参；output 是检查模型输出的工具字段是否正确，error schema 是为了保证错误能够正常记录和修复。

**评分与点评：**

- ✅ Input 的"告诉模型什么时候调用、如何传参"方向正确。
- ❌ "input 是 name / description / arg 三个参数"混淆了工具定义与 Input Schema：name、description 是工具定义字段，Input Schema 只是其中的 parameters 部分，约束的是模型可填写的参数（字段、类型、枚举、范围、必填条件）。
- ❌ **Output 归属答错了**：Output Schema 验收的是**业务函数（handler）的返回值**，不是"模型输出的工具字段"。模型输出由 Input Schema 约束；Output Schema 卡在 handler 与 Tool Result 之间，保证成功结果结构稳定、下一轮 Loop 可直接消费。这是本题主要失分点。
- ⚠️ Error 太泛：要点是 `code` + `retryable` 的分类驱动恢复——`INVALID_ARGUMENT` 可修正重调、`PERMISSION_DENIED` 必须停止、`TIMEOUT/UPSTREAM_ERROR` 仅幂等条件下有限重试、`INVALID_OUTPUT` 是工程故障不能让模型猜。

**更优答案（两分钟版）：**

> 三份 Schema 卡在链路的三个位置。Input Schema 在模型和 Runtime 之间，约束模型可以填什么参数——字段、类型、枚举、范围和必填条件，拦截错误调用；name 和 description 负责让模型选对工具，Schema 负责让参数填对。Output Schema 在 handler 和 Tool Result 之间，验收的是业务函数的返回值而不是模型输出，保证成功结果是一份稳定协议，Agent Loop 能直接消费，而不是随意字典。Error Schema 在失败和下一轮决策之间，用 code 加 retryable 统一失败分类和恢复语义：参数错误可以修正重调，权限不足必须停止，超时只有幂等时才能有限重试，输出违约是工程故障要记下来排查，而不是让模型猜缺了什么字段。

## Q4. 为什么权限和审批不能作为模型参数？（8 / 10）

**我的回答：**

> 权限和审批必须控制在程序之中，不能让模型自己创建权限和审批自己，这样容易绕过控制。

**评分与点评：**

- ✅ 核心答对：权限/审批属于程序侧可信上下文；模型不能自授权、自审批；否则控制被绕过。本题是五题中答得最好的。
- ➕ 可补强：① 数据来源——权限、角色、审批状态来自登录态或服务间身份，由 Harness 注入 Execution Context，模型不可填写；② 威胁场景——提示注入或幻觉时，"role=admin""approved=true" 就是一次越权；③ 拒绝时机——权限/审批检查必须发生在 handler 之前。

**更优答案（两分钟版）：**

> 权限和审批是可信上下文，只能来自登录态或服务间身份，由 Harness 注入 Execution Context。如果把 user_id、role、approved 放进 Input Schema 让模型填，等于让不可信输入自我声明"我是管理员、本次已审批"——一次提示注入或幻觉就能完成越权，而且审批环节被模型一句话跳过。正确做法是：模型只填业务参数（订单号、条件），Runtime 执行前从可信上下文读取身份、权限和审批记录，在 handler 之前完成拒绝；两类数据必须物理分离，不能出现在同一份 Schema 里。

## Q5. 两个同名工具调用乱序完成时，`tool_call_id` 怎样防止结果错配？（4 / 10）

**我的回答：**

> tool_call_id 在 input 和 output 中都带上。

**评分与点评：**

- ✅ 唯一答对的直觉：调用方和结果方都要携带同一 ID。
- ❌ 术语不准：不是"input/output"，是 Assistant 消息里的 ToolCall 与 role=tool 的 ToolResult 消息携带同一 `tool_call_id`。
- ❌ 没答出机制——题目问的正是"乱序完成时怎么防错配"：并行执行时完成顺序 ≠ 生成顺序，Runtime 必须让调用 ID 跟随调用对象进入每个异步任务（如 `execute_bound` 把 `(call.id, result)` 绑定在同一协程返回值里），而不是等结果返回后按顺序猜。由此解决四件事：消息协议对应、解除生成/完成顺序耦合、区分成功与失败的恢复对象、建立 Trace 父子关系。

**更优答案（两分钟版）：**

> tool_call_id 是"模型提出的调用"和"写回结果"之间的关联键：Assistant 消息里的每个 ToolCall 带 ID，随后每条 Tool Result 必须带回它所回答的那次调用的原始 ID。并行执行时完成顺序不一定等于生成顺序——比如查询两个订单，第二个先返回，超时的后返回；如果按返回顺序配对，结果就错配了。所以 Runtime 在派发时就把调用 ID 绑进每个异步任务，哪个任务完成就用哪个任务的 ID 生成结果，顺序乱了也能精确配对。这同时解决了四件事：协议对应关系、生成与完成顺序解耦、成功和失败各自的恢复对象、Trace 的父子关系。
